# 阶段 1.1：统一异常处理与结构化日志

## 这一阶段在做什么

这一阶段让后端在「出问题时」也能表现一致：用户收到统一、可读、不泄露内部信息的错误响应；开发者在日志里看到请求路径、状态码、耗时和必要的错误堆栈。

如果没有这一层，不同接口可能返回不同格式的错误，前端难以统一处理；服务器出错时也可能只剩一句「失败」，无法定位原因。

## 主要文件

- `backend/app/core/errors.py`：定义业务错误码、`AppError` 和全局异常处理器。
- `backend/app/core/logging.py`：配置 JSON 日志和请求日志中间件。
- `backend/app/main.py`：把异常处理器和日志中间件接入应用。
- `backend/tests/test_errors.py`：验证正常错误、参数错误和未知异常等场景。

## 用到的主要知识

### 1. 异常与全局异常处理器

业务代码发现不能继续执行时，可以抛出 `AppError`，例如「令牌无效」或「库存不足」。FastAPI 的全局异常处理器接住它，再转换成统一 JSON。

这样业务函数不需要每层都返回错误字典，也不需要每个路由重复写 `try/except`。

### 2. HTTP 状态码与业务错误码

两者用途不同：

- HTTP 状态码给浏览器、网关和 HTTP 客户端使用，例如 401 表示未认证，404 表示资源不存在，500 表示服务器错误。
- `code` 是项目内部的精细错误码，例如 40101 表示令牌无效，40102 表示用户名或密码错误。

因此响应可能同时表现为「HTTP 401 + 业务码 40102」，既符合 HTTP 规范，也方便前端精确提示。

### 3. 为什么服务器错误不能直接返回堆栈

堆栈包含文件路径、函数名，有时还会带出 SQL 或配置线索。它对开发者排查很有用，但不应暴露给访问者。因此系统采用：

- 前端收到：`服务器内部错误`。
- 服务端日志：记录完整堆栈和请求上下文。

### 4. 参数校验错误

请求字段缺失或类型不对时，FastAPI / Pydantic 会抛出 `RequestValidationError`。本项目把它转换为业务码 40001，并把字段级细节放进 `data.errors`，方便前端指出哪个输入框有问题。

### 5. 中间件与请求日志

中间件像请求经过的「公共通道」：请求进入路由前先经过它，响应离开前也经过它。因此它很适合统计一次请求的方法、路径、最终状态码和耗时。

日志采用 JSON，是为了以后容易被工具检索。例如可以按 `status_code=500` 或某个路径筛选，而不是只能阅读一大段自由文本。

### 6. 中间件和异常处理器的配合

项目先注册异常处理器，再添加请求日志中间件。这样日志记录到的是异常转换后的真实 HTTP 状态码，而不是把所有异常都误记为同一种结果。

## 一次出错请求怎样流动

以业务异常为例：

```text
请求进入
  → 请求日志中间件开始计时
  → 路由 / service 抛出 AppError
  → 全局异常处理器生成统一错误 JSON
  → 中间件记录路径、状态码、耗时
  → 前端收到响应
```

## 如何验证

```bash
cd backend
.venv/Scripts/python.exe -m ruff check .
.venv/Scripts/python.exe -m pytest tests/test_errors.py -v
```

测试覆盖：业务异常格式、参数校验格式、未知异常不泄露堆栈、未知路由也使用统一格式。

## 对后续开发的意义

后续所有模块都直接复用这套约定：service 只负责抛出语义明确的 `AppError`，路由不重复处理错误，前端也能统一显示提示。新增业务时，重点放在业务规则本身。
