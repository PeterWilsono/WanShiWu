# 阶段 2.11：默认分类初始化与分类管理接口

## 这一步在做什么

记账不能只保存一个金额，还要知道这笔钱属于“餐饮”“交通”还是“工资”。本阶段实现分类的初始化和管理：

| 接口 | 作用 |
| --- | --- |
| `GET /api/v1/categories?type=expense` | 查询分类，可按收入或支出筛选 |
| `POST /api/v1/categories` | 新建自定义分类 |
| `PATCH /api/v1/categories/{id}` | 修改分类名称或图标 |
| `DELETE /api/v1/categories/{id}` | 删除允许删除的自定义分类 |

用户注册成功时，会自动初始化说明书规定的 10 个内置分类。

## 默认分类有哪些

支出分类：

```text
餐饮、交通、购物、居家、娱乐、医疗、学习、其他
```

收入分类：

```text
工资、其他
```

每个用户拥有自己的一套分类，而不是全系统共用一张表。这样用户 A 改名或新增分类，不会影响用户 B。

图标保存 `food`、`transport`、`salary` 等字符串标识，后续前端可以映射为图标组件，不在数据库里绑定具体 UI 图标库。

## 需要理解的知识

### 1. 为什么注册和默认分类要在同一事务中完成

如果只创建用户成功，分类却创建失败，就会出现“能登录但没有办法正常记账”的不完整账号。

注册流程现在是：

```text
插入用户
→ flush 取得用户 id
→ 添加该用户的默认分类
→ 一次 commit
```

`flush` 会把当前事务里的 SQL 发给数据库并取得自增 id，但还不等于最终提交。任何一步失败，整个事务回滚，不会留下半个账号。

初始化函数会检查已有 `(type, name)`，所以重复调用时只补缺失项，不重复插入默认分类。

### 2. 分类名称的唯一范围

数据库约束是：

```text
唯一(user_id, type, name)
```

因此：

- 同一用户的支出分类不能有两个“餐饮”；
- 同一用户的收入“其他”和支出“其他”可以共存；
- 不同用户可以各自拥有“宠物”分类。

业务层会先检查并返回 40901，数据库唯一约束再作为并发情况下的最终兜底。捕获 `IntegrityError` 时会回滚，避免会话停留在失败事务中。

### 3. 为什么分类类型不允许 PATCH

`income / expense` 决定分类能用于哪种账目。若直接把一个已经被支出记录引用的分类改成收入，历史数据会失去原本含义。

所以 PATCH 只允许修改：

- `name`；
- `icon`。

`type` 和 `is_default` 都不开放修改。内置分类可以改名，但不能删除。

### 4. 为什么被引用分类不能删除

如果删除“餐饮”，历史午餐账目还保存着对应的 `category_id`，统计和详情就无法正确解释这条记录。

本阶段删除前会检查所有引用，包括已经软删除的账目。历史记录即使不再显示，也仍是数据关系的一部分。

规则如下：

- 内置分类：返回 42201，“内置分类不可删除”；
- 被任何账目引用：返回 42201，“已有账目引用该分类，只能改名”；
- 未被引用的自定义分类：写入 `deleted_at`，执行软删除。

### 5. 用户隔离与统一 404

所有查询都包含当前 `user_id` 和 `deleted_at IS NULL`。修改或删除其他用户、不存在、已删除的分类，都返回相同的 40401，避免越权访问和信息探测。

## 代码如何配合

- `auth/service.py`
  - 注册时先 flush 用户，再调用生活模块 service 初始化默认分类；
  - 用户和分类在同一事务提交。
- `life/schemas.py`
  - 新增分类创建、修改和响应 Schema；
  - 名称去空白，图标可清空，限制字段长度。
- `life/service.py`
  - 定义默认分类；
  - 实现列表、唯一性检查、新建、修改、引用检查和软删除。
- `life/router.py`
  - 注册四个分类接口并复用统一认证与响应。
- `tests/test_life_categories_api.py`
  - 覆盖默认初始化、筛选、唯一范围、非法参数、未登录、越权、内置保护、历史引用和软删除。
