# 阶段 2.4：完成待办与周期性待办

## 这一步在做什么

本阶段新增：

```text
POST /api/v1/todos/{todo_id}/complete
```

普通待办完成后变为 `done` 并记录完成时间。周期性待办除了完成当前记录，还会自动生成下一次待办。例如完成“每天背 20 个单词”后，系统会保留今天的完成记录，同时创建明天的同一项待办。

## 为什么不用 PATCH 代替完成接口

PATCH 适合修改普通字段，而“完成一个周期待办”包含一组业务动作：

1. 检查当前待办是否允许完成；
2. 写入当前记录的 `done` 和 `completed_at`；
3. 根据周期计算下一次截止时间；
4. 创建下一次 `pending` 待办；
5. 保证这些操作要么全部成功，要么全部撤销。

因此使用专用的动作接口 `POST /complete`，比让前端自行 PATCH 再 POST 更安全，也把业务规则集中在后端 service 中。

## 返回结果

普通待办：

```json
{
  "code": 0,
  "message": "完成成功",
  "data": {
    "todo": { "id": 1, "status": "done" },
    "next_todo": null
  }
}
```

周期待办的 `next_todo` 是新记录，包含新的 `id`、截止时间和初始状态。标题、备注、优先级、周期和标签会从当前记录复制。

## 需要理解的知识

### 1. 什么是数据库事务

事务把多次数据库修改视为一个整体。本阶段的两次修改是：

- 更新当前待办；
- 插入下一次待办。

如果第二步失败，只完成第一步会产生错误状态：用户看到任务已完成，却没有下一次任务。代码在提交失败时执行 `db.rollback()`，撤销整个事务，保证不会出现“只做了一半”。

### 2. 每日、每周和每月如何顺延

- 每日：原 `due_at` 加 1 天；
- 每周：原 `due_at` 加 7 天；
- 每月：月份加 1，日期保留，但不能超过目标月天数。

每月不能简单加 30 天，因为月份长度不同。例如：

- 2026-01-31 → 2026-02-28；
- 2024-01-31 → 2024-02-29（闰年）；
- 2026-12-31 → 2027-01-31（跨年）。

计算使用 Python 标准库 `calendar.monthrange` 获取目标月实际天数，没有新增依赖。

本阶段按说明书要求只顺延一个周期，不根据当前时间循环补齐多个过去周期。

### 3. 为什么周期待办必须有截止时间

下一次时间需要从原 `due_at` 计算。如果没有基准时间，“明天的任务”或“下个月同一时刻”都无法确定。因此：

- 普通待办没有截止时间也能正常完成；
- 周期待办没有截止时间时，完成接口返回 HTTP 422、业务码 42201；
- 出错后当前记录保持 `pending`，不会生成新记录。

### 4. 为什么重复完成返回 409

只有 `pending` 状态允许完成。已完成或已取消的记录再次调用完成接口，会返回 HTTP 409、业务码 40901。

409 表示请求与资源当前状态冲突。这个检查避免用户重复点击时生成多条下一次待办。

### 5. 新记录不是修改原记录

完成周期待办后保留原记录，而不是直接把原记录的截止时间改到未来。这样历史列表能证明“哪一次已经完成”，新记录则代表“下一次仍待完成”。每次完成都会形成一条独立历史。

## 代码如何配合

- `life/service.py`
  - `advance_due_at`：只负责周期时间计算；
  - `complete_todo`：负责状态检查、业务规则、创建下一次实例和事务控制。
- `life/schemas.py`：新增 `TodoCompleteResponse`，明确返回当前记录和可选的新记录。
- `life/router.py`：注册完成接口，不包含数据库查询或周期判断。
- `tests/test_life_todo_complete.py`：覆盖普通完成、周期顺延、重复完成、无截止时间、未登录、越权和事务回滚。
