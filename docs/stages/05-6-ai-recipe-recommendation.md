# 阶段 5.6：AI 菜谱推荐与库存重核算

## 目标

实现 `POST /api/v1/pantry/recipes`：读取当前用户的真实库存，优先把临期食材交给模型参考，结合人数和可选口味偏好，一次返回三道结构化家常菜谱。

## 为什么不直接相信模型

大模型擅长生成菜名和步骤，但它给出的“有库存／缺料”只是文本判断，不能作为数据库事实。本任务采用两层结果：

1. **模型候选**：菜名、分钟数、预计用量、预计缺料和步骤。
2. **代码重核算**：把候选中的同名同单位需求合并，再与当前用户的 active 库存逐项比较，重新生成 `uses` 和 `missing`。

例如模型认为需要 3 个鸡蛋，而当前用户只有 2 个，最终返回 `uses=2`、`missing=1`。其他用户的 10 个鸡蛋不会进入库存快照，也不会用于补足缺口。菜谱是备选关系，因此不会把三道菜的用量相互累计扣除。

## 输出校验与失败处理

- 根节点必须是对象，且只能包含 `recipes`；必须恰好三道。
- 每道菜只能包含规定的五个字段；分钟数、用量、固定单位、步骤数量和文本长度均有约束。
- 禁止额外字段、非正数数量、错误单位和 Markdown 代码围栏。
- 第一次 JSON 解析或 Schema 校验失败时，要求模型重新输出一次；第二次仍失败返回 `50202`。
- 模型调用统一经过 `LLMClient`，使用 `module=pantry`、`purpose=recipe` 和 JSON response format，沿用限额、超时与审计能力。

## 主要文件

- `backend/app/llm/prompts/recipe.txt`：独立菜谱 Prompt、JSON 结构和示例；明确库存与偏好只是不可信数据。
- `backend/app/modules/pantry/recipe_service.py`：库存快照、Prompt 消息、两次校验机会和库存重核算。
- `backend/app/modules/pantry/schemas.py`：菜谱请求、公开响应和模型输出 Schema。
- `backend/tests/test_pantry_recipes_api.py`：合法输出、七类非法结构、重试、库存缺口、临期排序和用户隔离测试。

- 后端全量测试：274 项通过。
- Ruff：通过。

## 当前边界

推荐结果不保存为数据库表；每次调用生成新的候选。最多将临期优先的前 200 个有效批次放入上下文，避免库存很大时无限扩张 Prompt。前端菜谱卡片将在下一小任务接入。
