# 阶段 2.17：reminders 数据层与日程提醒联动

## 这一步做什么

建立提醒表，并让日程上的“提前提醒分钟”真正生成提醒记录。此前这个字段只是保存和展示，本阶段开始具备后续到点通知所需的数据。

## 表结构

`reminders` 保存：目标类型（event/todo/custom）、目标 ID、提醒时间、展示文案、触发时间、已读时间，以及通用的用户、创建更新时间和软删除字段。

- `(fired_at, remind_at)` 索引用于下一步扫描“已到点但未触发”的记录。
- `(user_id, target_type, target_id)` 唯一约束保证一个日程只有一条提醒。
- 目标 ID 不设外键，因为 event/todo/custom 是不同类型的目标，由对应模块 service 维护一致性。

## 时间如何计算

```text
remind_at = event.start_at - remind_before_min 分钟
```

日程开始时间和提醒时间都使用带时区的 UTC。比如北京时间 09:00、提前 15 分钟，数据库保存的提醒时间是前一天 UTC 01:00 再减 15 分钟对应的绝对时刻。

## 联动规则

- 新建日程：日程与提醒在同一事务中创建。
- 修改标题：更新提醒文案，提醒时刻未变时保留触发和已读状态。
- 修改开始时间或提前分钟：重新计算提醒时刻，并清空旧的触发、已读状态。
- 清空提醒分钟：软删除提醒。
- 再次设置提醒：恢复原目标记录并重置状态，避免唯一约束冲突或重复提醒。
- 删除日程：同事务软删除对应提醒。

事务的意义是“日程和提醒要么一起成功，要么一起失败”。测试模拟提交异常后，数据库不会留下只有日程或只有提醒的半完成状态。

## 迁移与既有数据

Alembic 迁移 `19a609c8c9a0` 已应用到开发数据库。迁移还会为升级前已经设置提醒分钟、且未删除的日程补齐提醒，不会让旧数据因加表而失效。

## 验证

新增 6 个测试场景，覆盖 UTC 计算、无提醒、标题修改、重新排期、清空恢复、删除和事务回滚。完整后端回归 **198 项全部通过**，Ruff 检查通过。

当前边界：本阶段只实现 event 联动；todo/custom 是表结构预留，未额外发明业务规则。扫描触发和通知接口在 2.18 实现。
